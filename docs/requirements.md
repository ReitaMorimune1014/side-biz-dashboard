# 副業管理ダッシュボード 要件(v1)

副業の案件・売上・稼働時間を1か所で管理する、自分用の管理画面アプリ。公開デモはダミーデータのみ。

## 目的
- 自分が使う: 案件・稼働時間・売上を管理し、週の稼働目標(初期5時間)の達成を確かめる。
- 案件の応募で見せる: 認証、認可、CRUD、集計、自動テストを、公開デモとGitHubで示す。

## ロール
- オーナー: 自分のデータを全て操作できる。誰でも登録でき、自分のデータだけが見える。
- 閲覧者: 公開デモ用。ダミーデータの閲覧のみ。
- 認可は、画面を隠すだけにせず、サーバー側とデータベース(行単位の権限)で強制する。

## 業務ルール
- 案件の状態: 見積 → 受注 → 進行 → 納品 → 請求済 → 入金済、と失注。新しい案件は見積から始まる。
- 状態は、一覧のプルダウンと編集画面から、どの状態へでも変更できる。
- かんばんのボタンは、次の状態へ進む(失注にするのは見積と受注から)と、1つ前の状態に戻す(失注からは見積か受注へ)だけを出す。
- 売上は、売上日ベースで集計する。案件が納品・請求済・入金済のとき、案件の金額を売上日の売上として数える。
- 売上日は、納品より前から納品以降に変えた日(日本時間)を自動で入れ、編集画面で直せる。納品以降の中で状態を変えても売上日は変えず、納品より前に戻したら消す。
- 時給は、期間の売上 ÷ 期間の稼働時間。見込みは、受注・進行と見積の金額を分けて合計する(失注は含めない)。
- ダッシュボードの「期限が近い納期」は、受注・進行の案件のうち、期限切れと今日から14日以内の納期を、近い順に出す。状態別の件数は、失注を含む7つの状態すべてを出す。
- 一覧(案件・顧客・稼働)の検索は、空白で区切った語をすべて含むものを出す。全角・半角と大文字・小文字は区別しない。条件は URL に残し、10件ずつページに分ける。
  - 案件: 題名・顧客名・メモで検索、状態で絞り込み、登録の新しい順・納期の近い順(未定は最後)・金額の高い順。
  - 顧客: 名前・メモで検索、登録の新しい順・名前順。
  - 稼働: 案件名・メモで検索、案件で絞り込み、日付の新しい順・古い順。
- CSV出力(案件・稼働): 一覧の今の検索・絞り込み・並び順のまま、ページに分けず全件を出す。UTF-8(BOM付き、Excelで文字化けしない)、改行はCRLF。ファイル名は「案件_YYYY-MM-DD.csv」「稼働_YYYY-MM-DD.csv」(日本時間の今日)。`=` `+` `-` `@` などで始まる文字列は、先頭に `'` を付けて数式として実行させない。閲覧専用のアカウントも出力できる。
  - 案件: 顧客、題名、金額、状態、納期、売上日、メモ。
  - 稼働: 日付、案件、顧客、分、時間(小数第2位まで)、メモ。
- 変更履歴(案件): 作成と変更のたびに、DB のトリガーが「操作(作成・変更)、変わった項目の変更前と変更後、日時」を記録する(画面からでも API を直接呼んでも残る)。記録する項目は、状態・題名・顧客・金額・納期・売上日・メモ。値が変わらない更新は記録しない。利用者は履歴を読めるだけで、追加・変更・削除はできない。案件ごとの履歴ページで新しい順に見られ、閲覧専用のアカウントも見られる。履歴は、この機能を入れた後の作成・変更から残る。
- 入力検証は、サーバーアクションと同じ検証関数を、送信前に画面でも実行する。エラーがあれば送信を止め、最初のエラーの項目へカーソルを移す。一度エラーが出た項目は、入力のたびに検証し直す。顧客や案件が存在するかなど、データベースを見る検査はサーバーだけで行う。
- 公開デモ: 本番と別の Supabase・Vercel のプロジェクトで動かし、ダミーデータだけを入れる。ログイン画面の「デモを見る」ボタンで、共有の閲覧専用アカウントに入る(パスワードはサーバーの環境変数に置き、画面には出さない)。デモではメールでのログイン・新規登録は受け付けない。
- 閲覧専用: Auth の `app_metadata.read_only` で判定する(本人には変えられない)。DB(RLS)・サーバー・画面のすべてで書き込みを拒否し、パスワードとメールアドレスも変えられない。
- 週は月曜始まり(設定で変更可能にする)。
- 金額は、整数の円(税込)。消費税の計算は、v1では行わない。
- 稼働時間は、分単位の整数で保存し、表示は時間にする。

## データ(項目のみ)
- 顧客: 名前、メモ、削除日時
- 案件: 顧客、題名、金額、状態、納期、売上日、メモ
- 稼働: 案件、日付、分数、メモ
- 設定: 週の目標時間、週の開始曜日
- 変更履歴: 対象、操作、変更前後、日時
- 全てのデータに所有者の識別子を持たせ、権限の判定に使う。個人情報は、顧客の名前とメモのみ。

## 非機能要件
- セキュリティ: 認証は外部サービスに任せる。認可はデータベース側でも強制し、認可のテストを書く。秘密情報はリポジトリに入れない。
- プライバシー: 実データは、公開リポジトリと公開デモに入れない。
- テスト: 認可、状態遷移、集計の単体テストは必須。主要な流れのE2Eテストを1本。
- CI: lint、型チェック、テスト、ビルドをPRごとに自動で実行する。
- アクセシビリティ: キーボード操作、十分なコントラスト、フォームのラベル。
- 公開: READMEに、起動手順、構成図、ER図、設計理由、既知の課題を書く。

## このプロジェクトのルール

### 作業の進め方
- 実装の前に、必ず `docs/requirements.md` を読む。1つの依頼は、要件のID1つだけ。
- 実装の前に、方針(変更するファイル、設計理由、代替案)を示して、確認を待つ。
- ブランチは `feature/<ID>-<内容>`。受け入れ条件を満たすテストを書く。
- 完了したら、PRの説明に「目的・設計理由・確認方法」を書く。
- 不明点は、推測で実装せず、実装の前に質問する。
- 新しいライブラリを足す前に、必要な理由を説明する。

### 安全のルール
- 認可は、画面を隠すだけにせず、サーバー側とデータベースの権限でも強制する。
- 秘密情報(secret key、service_role key)は、コードにも、`NEXT_PUBLIC_` の変数にも置かない。
- サーバー側のコードで、`supabase.auth.getSession()` を信用しない。ページの保護には `getClaims()`、データを書き換える操作には `getUser()` を使う。
- 業務ロジックは、画面から独立した関数にし、単体テストを書く。

## 認証の決定事項(F1)
- 認証は Supabase Auth。`@supabase/ssr` でCookieを使う。
- 環境変数は `NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`。
- Next.js 16 では、認証トークンの更新は `proxy.ts`(旧 middleware)で行う。
- 認証方式は、メールのリンク(パスワードを扱わない)。
- 保護された画面に、未ログインで入ったら、ログイン画面に移す。
