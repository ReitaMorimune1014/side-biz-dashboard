## 全PR共通のレビュー観点(マージ前に自分で確認する)
- 受け入れ条件を満たすテストがある。認可に関わる変更には、認可のテストがある。
- 自分で、変更したコードを、ファイルごとに説明できる。
- 秘密情報が含まれていない。`git diff` を読んだ。
- PRの説明に、目的・設計理由・確認方法がある。
- lint / typecheck / test / build が、CIで緑。

## F1の判断メモ
- サーバー側で `getSession()` を信用しない。ページの保護は `getClaims()`、重要な操作は `getUser()`。選んだ理由をPRに書く。
- `@supabase/ssr` は、既定でPKCE。メールのリンクは `signInWithOtp` で送り、コールバックで `exchangeCodeForSession` を呼ぶ。
- ログイン後の転送先(`next` などの引数)は、**同じサイト内の相対パスだけ**を許可する(外部へ飛ばされるのを防ぐ)。
- ログイン直後に、Next.jsのリンクの先読みが走る画面へ飛ばすと、サーバー側でセッションが見つからないことがある。**先読みのない1つの画面**へ転送する。
- ログアウトは、GETではなく、POST(またはServer Action)にする。

## F2の判断メモ
- 全てのテーブルに `user_id uuid not null default auth.uid()` を持たせ、auth.users を参照する。
- RLSを有効にし、select / insert / update / delete の4つのポリシーを、`auth.uid() = user_id` で書く(性能のため、`(select auth.uid())` の書き方が推奨される。公式で確認する)。
- service_role keyを、アプリのコードで使わない。
- テストは、2人のユーザーを作り、**Aが、Bの行を、読めない・書けない・消せない**ことを確認する。
- マイグレーションは `supabase/migrations/` にSQLで残す(権限もコードとして管理する)。ローカルでは `npx supabase start`(Dockerが必要)で検証する。

## 注意が必要な箇所
- 週の計算: 月曜始まり、日本時間(Asia/Tokyo)。日付と時刻の型を混ぜない。境界(日曜23:59と月曜0:00)のテストを書く。
- 金額: 整数の円。小数を使わない。
- 状態遷移: 画面ではなく、サーバー側の関数で強制する。

## 環境の分離
- 開発・テスト: ローカルのSupabase(使い捨てできる)。
- 公開デモ: 別のSupabaseプロジェクト + ダミーデータ + 閲覧専用のユーザー。実データは入れない。
